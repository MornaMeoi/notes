# Инварианты
## Суть
Инвариант типа — утверждение о состоянии объекта, которое методы обязаны **сохранять**, а весь остальной код вправе **предполагать без проверки**.
Вторая половина и есть смысл: инвариант существует, чтобы не проверять одно и то же снова и снова.
## Почему так
Без инварианта каждый метод обязан сам убедиться, что состояние корректно. В [[L02. Указатели и ссылки]] это показано на списке: `length` должен проверить отсутствие петли алгоритмом Флойда, `reverse` — проверить снова, следующий метод — опять. Каждый платит `O(n)` за паранойю, и эта плата накапливается.
Инвариант переносит проверку в **одну точку** — конструктор, — и дальше все методы работают бесплатно.
### Когда именно он обязан выполняться
Формулировка «всё время жизни объекта» неточна. Точнее так:
> Инвариант обязан выполняться на **границах** публичных методов — до входа и после выхода.
> Внутри метода он может быть временно нарушен.

Иначе не написать ни одного нетривиального метода: `reverse` рвёт связи по ходу работы, `std::vector::push_back` при реаллокации на миг держит два буфера, красно-чёрное дерево после вставки временно не сбалансировано, пока идут повороты.
Отсюда прямое следствие, важнее самого определения: **если метод бросит исключение в момент, когда инвариант нарушен, объект останется в неконсистентном состоянии**.
Именно это и означает базовая гарантия из [[Exception safety]] — «объект остался консистентным».
### Кто устанавливает
Конструктор — единственная точка входа в валидное состояние. Если из переданных аргументов инвариант установить невозможно (три точки полигона на одной прямой), у конструктора два законных выхода:
- **бросить исключение** — объект не рождается вовсе, деструктор для него не вызовется;
- **не быть конструктором**: фабричная функция, возвращающая `std::optional` или `std::expected`, — когда невалидный ввод это норма, а не исключительная ситуация.
Чего делать нельзя — молча принять плохие аргументы. Тогда объект родится в невалидном состоянии, а ошибка проявится позже и в другом месте.
Проверку стоит поднять в компиляцию везде, где это возможно (`consteval`-конструктор, `static_assert` по шаблонному параметру). Но для данных, пришедших в рантайме, компиляция помочь не может — остаётся исключение.
## Примеры

| Тип | Инвариант |
|---|---|
| Полигон | вершины упорядочены по кругу |
| Двусвязный список | нет петель, ноль-терминирован, `next`/`prev` согласованы |
| `std::set`, `std::map` | элементы упорядочены компаратором и уникальны |
| `std::vector` | `size() <= capacity()`, элементы лежат непрерывно |
| `const int&` | под ней корректное **и не вам принадлежащее** целое |

`std::set` показывает высший пилотаж: язык не просто позволяет держать инвариант, а делает его нарушение **невозможным**. Итератор `set` константен, а в `map` ключ константен внутри `pair<const K, V>` — изменить ключ нельзя физически, потому что это сломало бы порядок.
## Подводные камни

**Протечка ссылки на состояние.** `private` — необходимое условие, но не достаточное.
Инкапсуляция ломается не доступом к полям, а выдачей ссылки на них:

```cpp
class Polygon {
    std::vector<Point> verts;                          // инвариант: упорядочены по кругу
public:
    std::vector<Point>& vertices() { return verts; }   // инварианта больше нет
};
```

Ни `private` не тронут, ни каста нет — а состояние теперь меняет кто угодно.
То же делают `data()`, неконстантные итераторы и любой возврат указателя внутрь.
**Исключение при нарушенном инварианте** — см. выше. Проектировать метод стоит так, чтобы всё, что может бросить, случалось **до** первого изменения состояния (линия Калба, [[RAII]]).
**Вызов собственного публичного метода изнутри**, пока инвариант нарушен. Метод вправе рассчитывать на корректное состояние, а получит порванное. Особенно опасно с виртуальными вызовами.
**`private` не защищает от `reinterpret_cast`.** Память линейна, и приведя указатель
на объект к `char*`, можно затоптать что угодно (по крайней мере для standard-layout
и trivially copyable типов). Это не дыра, а свойство языка: `private` — инкапсуляция
**на уровне имён, а не памяти**. Это механизм дисциплины, а не безопасности — защита от ошибки, не от злого умысла. Работает целиком на этапе компиляции и потому стоит ноль.

## Связано с
- [[Время жизни]] — два взгляда на один отрезок: время жизни отвечает, *когда* объект существует, инвариант — *что о нём известно*, пока он существует. Инвариант вступает в силу, когда завершился конструктор, и перестаёт быть гарантированным, когда начался деструктор. Обращение по висячему указателю не «нарушает инвариант» — там нет объекта, рассуждать не о чем, это UB
- [[Exception safety]] — базовая гарантия это и есть «инварианты уцелели»
- [[RAII]] — инвариант «ресурс захвачен ровно один раз», который держит сам тип
